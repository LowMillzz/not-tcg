## Feasibility verdict

**Conditionally feasible with public macOS APIs.** There is a documented route to selecting an auction window, taking a still on a global shortcut, cropping locally, and displaying an unfocused result. macOS 14 is a plausible minimum for the combination of ScreenCaptureKit's original still API and system content picker. This is an architectural input, not an approved deployment target or stack choice. [SCScreenshotManager](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager), [system picker](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker), [non-activating panel](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel).

Three claims remain unproven: reusable picker consent for repeated standalone stills without an active stream; actual capture of each auction platform's video in the chosen browser/region; and the roughly five-second end-to-end deadline. Neither Apple API availability nor a supported card catalog establishes those claims. Both raw English Pokémon singles and graded slabs remain launch requirements. Capture tests must include readable card details and slab labels; a capture limitation cannot silently remove either category.

**Proposed baseline:** hotkey-only still acquisition, no audio, an explicit capture/upload indicator, an in-memory local crop, and no screenshots retained by default. A low-rate stream is an alternative to investigate only if still capture cannot meet consent or latency needs. It continuously acquires frames while active even if inference runs only on a hotkey, so adopting it requires an explicit product decision about the confirmed hotkey scope.

| ScreenCaptureKit / `SCStream` / desktop-independent window filter | 12.3+ | Older-system support would require stream-based acquisition and different selection/onboarding. | Original `SCScreenshotManager.captureImage(contentFilter:configuration:completionHandler:)` | 14.0+ | Asynchronous single image, using `SCContentFilter` and `SCStreamConfiguration`; creating a persistent `SCStream` is not required for the screenshot call. | `SCContentSharingPicker`; filter `contentRect` and `pointPixelScale` | 14.0+ | System selection and explicit point-to-pixel metadata are available at the proposed floor. [Picker](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker), [rect](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/contentrect), [scale](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/pointpixelscale) |

[API](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager/captureimage(in:completionhandler:)) |
| `SCScreenshotConfiguration` / `captureScreenshot(contentFilter:configuration:completionHandler:)` | 26.0+ | Newer screenshot configuration must be availability-gated. Its `sourceRect` is described in logical display points; do not back-port these semantics to the older stream configuration. [Configuration](https://developer.apple.com/documentation/screencapturekit/scscreenshotconfiguration), [capture](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager/capturescreenshot(contentfilter:configuration:completionhandler:)), [rect](https://developer.apple.com/documentation/screencapturekit/scscreenshotconfiguration/sourcerect) |
| Apple's current “Capturing screen content in macOS” sample | Sample requires macOS 15+ and Xcode 16+ | Those are the current sample's prerequisites, not the introduction versions of still capture, streaming, or the picker. [Sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) |

No Apple-silicon-only restriction is stated for the original still/window APIs above. Supporting Intel is nevertheless a release commitment requiring compatible OS versions, an `x86_64` build of every native dependency, and actual tests. Apple's universal-binary documentation distinguishes `arm64` and `x86_64` slices; Rosetta testing is possible on Apple silicon but does not replace real Intel capture/performance validation. [Universal binaries](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary).

Current toolchain implications differ from older universal-binary guidance: Xcode 27 release notes say Xcode itself runs only on Apple silicon, while its macOS SDK can back-deploy universal apps to macOS 12+. For deployment targets 27+, standard architectures no longer include `x86_64` by default. Apple also identifies Tahoe as the final Intel macOS release. Thus a universal app targeting 14 remains a different choice from requiring the newest OS. [Xcode 27 notes, Intel Deprecation](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes), [WWDC26, 40:28–40:55](https://developer.apple.com/videos/play/wwdc2026/102/).

## Still capture versus a low-rate stream

| Aspect | Hotkey-triggered still | Low-rate stream |
| --- | --- | --- |
| Acquisition | Call the asynchronous screenshot API after the shortcut. | Keep an `SCStream` active and select a suitable frame on the shortcut. |
| Scope/privacy | Fits acquisition only on request; selected-window pixels outside the crop may exist briefly in local memory. | Acquires content between requests; a one-frame cache is still background acquisition. Requires visible session controls and a scope decision. |
| Freshness | Must measure delay from key event to image completion; a completed call alone does not prove the auction player is live. | A throttled frame may predate the key event. Request/wait for a post-trigger complete frame or enforce a measured freshness rule; never label a cached frame as captured “now.” |
| Permission reuse | Original API does not need a stream, but picker session lifetime across independent calls is not established by the reviewed docs. | Picker is explicitly designed to manage capture streams and session changes. |
| Cost | No stream lifecycle to keep active; actual startup overhead is unmeasured. | Frame throttling is supported, but CPU, memory, energy, and first-frame latency remain unmeasured. |

Apple describes the still API as a replacement for creating a stream when taking a screenshot. `minimumFrameInterval` throttles stream updates by specifying a reciprocal maximum frame rate; it is not a guarantee that a fresh frame arrives at that interval. Streams expose frame status and display-time metadata. These facts support the comparison; the performance and freshness policies above are proposals. [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10136/), [minimum interval](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/minimumframeinterval), [frame status](https://developer.apple.com/documentation/screencapturekit/scframestatus), [display time](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo/displaytime).

`idle` means no new frame because the display did not change; `blank` means the display is blank. Neither is a documented universal detector for DRM, a paused auction player, or the wrong lot. A stream implementation needs status handling plus source/session validity and an explicit stale/unavailable state. [Idle](https://developer.apple.com/documentation/screencapturekit/scframestatus/idle), [blank](https://developer.apple.com/documentation/screencapturekit/scframestatus/blank).

## Selection, permissions, and recovery

**Documented:** Apple recommends the shared system content picker. Its available modes select windows, applications, or displays; the reviewed mode list has no arbitrary rectangle mode. Use system selection for the source, then provide an app-owned crop selection within that source. This distinguishes selecting what the app may capture from selecting which pixels to upload. [Picker](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker), [modes](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpickermode).

Apple's WWDC23 privacy explanation says picker selection permits capture of the chosen content for the capture session without a separate broad Screen Recording grant. The system supplies a sharing indicator and controls to change or end the session. This does **not** document permission forever, across app launches, after cancellation, or after stopping a stream. The current framework overview also instructs developers to request screen recording permission and include `NSScreenCaptureUsageDescription`; its newer cross-platform guidance should be checked against the chosen macOS SDK and deployment floor during implementation. [WWDC23 privacy, 5:45–7:30](https://developer.apple.com/videos/play/wwdc2023/10053/), [framework overview](https://developer.apple.com/documentation/screencapturekit).

**Unresolved experiment:** obtain a picker filter with broad permission absent, take several standalone stills, stop/restart any session, then repeat and relaunch. Determine precisely when selection/authorization must recur. The reviewed documentation does not promise the “select once, independent stills indefinitely” behavior. If that fails, the product must choose explicit broad Screen Recording onboarding, re-selection, or an explicitly approved active session. Do not hide a low-rate stream to preserve consent.

For a broad-grant path, Apple's sample describes the first Screen Recording prompt and a sample restart after grant. System Settings lets users turn screen/audio recording access on or off. Do not assume identical restart behavior or a fixed reauthorization/reminder interval on every macOS release. [Sample onboarding](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [permission settings](https://support.apple.com/guide/mac-help/control-access-screen-system-audio-recording-mchld6aa7d23/mac).

ScreenCaptureKit documents permission denial and user-stopped errors; `SCStreamDelegate` reports termination. **Proposed recovery:** clear any ready/cached-capture state on cancellation, denied access, closed source, or stream failure; cancel pending uploads where possible; explain the state without taking bidding focus; allow an intentional reselect/retry. Revocation timing and exact errors for still calls require measurement. [Errors](https://developer.apple.com/documentation/screencapturekit/scstreamerror/code), [stop callback](https://developer.apple.com/documentation/screencapturekit/scstreamdelegate/stream(_:didstopwitherror:)).

The restricted Persistent Content Capture entitlement is described for VNC apps and requires Apple approval. It is not a proposed permission shortcut for this companion. [Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.persistent-content-capture).

## Geometry and content edge cases

| Case | Documented behavior | Product implication / experiment |
| --- | --- | --- |
| Single selected window | A desktop-independent filter captures only that window. Apple describes stream capture as including the full window when covered or moved off-screen/across displays; child/pop-up windows are separate. | Prefer window identity over a fixed desktop rectangle when following movement. Verify equivalent still behavior and browser fullscreen/Picture-in-Picture changes. Do not infer that a new player window is the original selection. [Filter](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/init(desktopindependentwindow:)), [WWDC22, single-window example](https://developer.apple.com/videos/play/wwdc2022/10155/) |
| Resize | Apple describes window-stream output being hardware-scaled into the configured output frame as the source resizes. | This does not preserve a card/player crop semantically. Proposed safe MVP: invalidate/reconfirm the crop after size/layout changes. Movement without size change can preserve window-relative crop coordinates, subject to tests. [WWDC22](https://developer.apple.com/videos/play/wwdc2022/10155/) |
| Cropping with the original API | `SCStreamConfiguration.sourceRect` is explicitly ignored for single-window capture; the full window bounds are captured. | Crop the returned image locally before encoding/upload. Do not assert that only the crop ever enters app memory. Display-region capture can use a source rect, but it is tied to display coordinates rather than automatically following an auction window. [Source rect](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/sourcerect) |
| Minimized window | Apple says the window stream pauses when minimized and resumes when restored. | Never reuse its last frame as a new lot. Standalone still behavior is unverified. Proposed MVP requires the selected auction to remain visible and rejects unavailable/stale captures. [WWDC22](https://developer.apple.com/videos/play/wwdc2022/10155/) |
| Scaling / multiple displays | Filter `contentRect` uses screen points; `pointPixelScale` translates points to pixels. AppKit provides per-screen backing conversion. | Avoid assuming 1 point = 1 pixel or using only the main display scale. Test Retina/non-Retina movement, non-default scaling, negative desktop origins, display removal, and crops near edges. Initially reject a display-region selection spanning displays unless implemented and tested explicitly. [Rect](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/contentrect), [scale](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/pointpixelscale), [backing conversion](https://developer.apple.com/documentation/appkit/nsscreen/convertrecttobacking(_:)) |
| Full-screen Spaces / hidden tabs | Reviewed capture documentation does not guarantee every browser fullscreen, tab-throttling, PiP, or Space transition. | Test both native fullscreen Spaces and in-player fullscreen. Revalidate source identity and geometry. An occlusion guarantee does not guarantee the browser continues rendering fresh auction video. |
| Protected/unavailable video | Apple notes that some apps prevent recording. AVPlayer separately documents Clear Key video capture being disabled by default and distinguishes FairPlay protection. | An onscreen playable video can be absent from a capture. No evidence establishes DRM configuration for Whatnot, TikTok Live, or eBay Live. Show “capture unavailable,” never invent a recognition/price result or attempt a protection bypass. [Apple screen-recording limitations](https://support.apple.com/en-gb/102618), [AVPlayer capture policy](https://developer.apple.com/documentation/avfoundation/avplayer/allowscaptureofclearkeyvideo) |
| Our result overlay | Display filters can exclude specified applications or windows; a single-window filter selects only the auction window. | Exclude the companion's app/windows in display capture and test overlap. Do not rely on `NSWindow.sharingType = .none`: Electron documents that ScreenCaptureKit can still capture protected Electron windows. [Application exclusion](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/init(display:excludingapplications:exceptingwindows:)), [Electron warning](https://www.electronjs.org/docs/latest/api/browser-window#winsetcontentprotectionenable-macos-windows) |

Proposed crop state should record source identity, source dimensions, crop coordinate convention, and display/scale information, with explicit invalidation rules. Persisting a region is not persisting authorization or proving the same auction/lot remains visible. Never silently substitute another display, another browser window, or a full-screen upload when the selection breaks.

## Global shortcut and focus constraints

A registered shortcut can be implemented without a general keyboard observer. Maintained first-party project evidence: KeyboardShortcuts identifies itself as sandbox/Mac App Store compatible and says it causes no permission dialogs. Its source uses `RegisterEventHotKey`; the inspected revision is `772133d9dbe800fdac0473226822994c5c162c58`, committed 2026-09-11. Its current manifest requires Swift tools 6.2 but targets macOS 10.15+, illustrating that compiler and deployment requirements differ. These are project claims and inspected code, not an App Review guarantee for our app. [Pinned README](https://github.com/sindresorhus/KeyboardShortcuts/blob/772133d9dbe800fdac0473226822994c5c162c58/readme.md), [registration source](https://github.com/sindresorhus/KeyboardShortcuts/blob/772133d9dbe800fdac0473226822994c5c162c58/Sources/KeyboardShortcuts/HotKey.swift), [manifest](https://github.com/sindresorhus/KeyboardShortcuts/blob/772133d9dbe800fdac0473226822994c5c162c58/Package.swift).

By contrast, Apple's `NSEvent` global monitor documentation requires accessibility access to monitor key-related events and says monitoring cannot prevent delivery to the target app. Therefore blanket Accessibility/Input Monitoring onboarding is not established as necessary merely by the global-hotkey requirement. Select the actual shortcut mechanism first. [Global event monitor](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:)).

**Proposed UX:** user-configurable modified non-media shortcut; explicit conflict/registration-failure handling; one request per intentional press; no key-repeat flood; no synthetic bids, clicks, or browser activation. Test keyboard layouts, occupied shortcuts, browser text fields, held keys, secure-input situations, and hotkey behavior in fullscreen. Electron's maintained documentation confirms background shortcut registration and reports failure when another app owns the shortcut; media keys have separate accessibility restrictions. [Electron globalShortcut](https://www.electronjs.org/docs/latest/api/global-shortcut).

For native results, an AppKit `NSPanel` with `.nonactivatingPanel` is documented not to activate its app. `ignoresMouseEvents` can make an output-only panel transparent to clicks. `.canJoinAllSpaces` and `.fullScreenAuxiliary` are relevant collection behaviors, but their existence does not prove all third-party fullscreen combinations. **Proposal:** render SwiftUI content in such a panel, show it without making it key, keep it away from bid controls, and move interactive correction/settings into an explicitly opened UI. Verify the browser remains frontmost and receives typing/clicks throughout capture and result arrival. [Non-activation](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel), [mouse events](https://developer.apple.com/documentation/appkit/nswindow/ignoresmouseevents), [all Spaces](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/canjoinallspaces), [fullscreen auxiliary](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/fullscreenauxiliary).

## Architecture inputs, without choosing a stack

| Concern | Native SwiftUI + AppKit | Cross-platform shell + native capture bridge |
| --- | --- | --- |
| OS integration | Direct access to ScreenCaptureKit, AppKit panels, and Swift callbacks. | Keep picker, crop coordinates, capture lifetime, and permission errors in a macOS-native component; marshal results/errors across a defined bridge. |
| Reusable work | Mac UI and OS glue; recognition/pricing domain logic can still have separate interfaces. | Shared web UI/domain code is possible, but the launch scope remains macOS-only and the bridge still needs macOS ownership and tests. |
| Capture API fidelity | Can explicitly use the macOS 14 still/picker APIs. | Do not equate shell APIs with identical floors/semantics. Electron's system-picker option is currently experimental and macOS 15+, although Apple's native picker begins at 14. Its ordinary desktop capture enumerates screens/windows and requires macOS consent. |
| Focus/overlay | Native non-activating panel behavior available directly. | Electron documents `showInactive`, non-focusable windows, and fullscreen-workspace visibility; native behavior still needs verification. Tauri exposes frontend-to-Rust commands and a global-shortcut plugin, but a ScreenCaptureKit bridge remains a proposed component here. |
| Release work | One native app/toolchain plus selected libraries. | Sign/package all helpers and native modules; Electron MAS builds have a distinct sandbox/signing workflow. Tauri also documents code signing/notarization. |

Sources: [Electron desktop capture](https://www.electronjs.org/docs/latest/api/desktop-capturer), [experimental system picker](https://www.electronjs.org/docs/latest/api/session#sessetdisplaymediarequesthandlerhandler-opts), [Electron window controls](https://www.electronjs.org/docs/latest/api/browser-window), [Electron MAS guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide), [Tauri commands](https://v2.tauri.app/develop/calling-rust/), [Tauri shortcuts](https://v2.tauri.app/plugin/global-shortcut/), [Tauri distribution](https://v2.tauri.app/distribute/).

The inference that native has fewer integration boundaries follows from direct framework access; no comparative latency, binary-size, memory, developer-effort, or reliability measurements were made. A shell does not remove Screen Recording consent, protected-video restrictions, AppKit focus issues, or the need for Mac CI. **Proposed bridge boundary:** native capture returns cropped bytes plus dimensions, capture timing, selection revision, and a structured error; the UI receives no uncropped desktop image. Keep provider credentials and upload authority out of an untrusted renderer. This is a design proposal, not implemented behavior.

## Distribution, signing, sandbox, and CI

**Direct distribution:** the normal Gatekeeper-friendly release path is Developer ID signing, hardened runtime, notarization, and a stapled ticket on the delivered artifact. Apple requires valid signatures for distributed executables, secure timestamps, and appropriate release entitlements; notarization is an automated security check, not App Review. Use `notarytool` or Apple's supported API rather than retired `altool` submission. App Sandbox is optional for notarized direct distribution. [Notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [distribution configuration](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution).

**Mac App Store:** App Sandbox is required, with store signing/submission and App Review. A sandboxed app needs the outgoing network client entitlement for AI/data endpoints, including a server on the same machine. This research found no basis to declare screen capture plus a registered shortcut categorically incompatible with sandboxing; neither does it establish approval of this entire product. Validate the capture bridge and shortcut in the actual sandboxed package. [Sandbox requirement](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [network client](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.network.client), [KeyboardShortcuts project claim](https://github.com/sindresorhus/KeyboardShortcuts/blob/772133d9dbe800fdac0473226822994c5c162c58/readme.md).

Apple's review rules require consent and a clear indication for recording user activity (§2.5.14), privacy disclosure/permission for personal data shared with third parties including AI (§5.1.2), and appropriate authorization under third-party service terms (§5.2.2). App retention and configured-provider retention must be explained separately; deleting local screenshots does not promise provider deletion. These are release inputs, not a determination of auction-platform terms or legal compliance. [Review guidelines](https://developer.apple.com/app-store/review/guidelines/).

Open source does not eliminate release costs: Apple lists Developer Program membership at USD 99/year, with regional pricing and limited organizational fee waivers. A release owner/team and funding choice remain human decisions. This cost is distinct from the prohibition on paid price-data dependencies. No enrollment, certificate, or credential action was taken. [Enrollment](https://developer.apple.com/programs/enroll/).

**Build/CI prerequisites:** a Mac with the selected Xcode/SDK, accepted setup/license, compatible compiler/package versions, and reproducible `arm64`/`x86_64` release builds if Intel is promised. Apple's checked support table lists Xcode 27.2 as requiring macOS Tahoe 26.6+ for the build host while allowing macOS 12–27 deployment; pin the actual supported toolchain at implementation. Signing identity/profiles and notary authorization belong only on authorized release hosts/CI. Linux devbox research/build tooling does not validate this app's Mac capture behavior. Headless compilation cannot prove picker consent, overlay focus, browser video capture, or revocation recovery; schedule interactive Mac tests separately. [Xcode compatibility table](https://developer.apple.com/xcode/system-requirements/), [Xcode 27 architecture notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes).

## Smallest later experiments

These are proposed follow-up tasks, **not performed or authorized by this report**. Future fleet Mac work must use the fleet computer-use playbook and linked macmini environment, verify host/account, and keep artifacts free of account/session material. Use an isolated disposable harness and user-authorized/public viewing content; no AI calls are needed to test acquisition, cropping, or focus.

1. **Consent and still viability.** On the proposed minimum OS and current supported OS, select one source through the system picker with broad recording permission absent; take repeated stills; end the session; retry; relaunch; deny/revoke access; close/reopen the source. Repeat with the explicit broad-permission path if required. Record prompts, restart requirements, errors, capture/session indicators, and whether capture stops. A decisive result chooses between standalone stills with appropriate onboarding and an explicitly reviewed alternative. Measure hotkey → capture completion → local crop with a visible time-changing test target; separate first capture from subsequent captures. A five-second recognition/pricing result remains untested.
2. **Viewing-platform gate.** For **each** of Whatnot, TikTok Live, and eBay Live, record country/region, macOS build, browser/version, viewer entry path, and whether the needed manual bid/purchase controls are actually available on that Mac. Proposed initial browsers: Safari and one Chromium browser; add Firefox if chosen for support. Capture several changing live frames in a normal window and player/native fullscreen, using a raw-card scene and a slab-label scene. Confirm video pixels are present and current, crops contain identifying details, and controls remain usable without focus transfer. If a platform cannot meet this gate, return the launch conflict to the human; do not infer support from pricing/catalog integration.
3. **Geometry and focus.** With a time-changing local test target, move/resize the selected window, cover it, minimize/restore, switch tabs/Spaces, enter fullscreen/PiP, move between Retina/non-Retina/scaled displays, disconnect a display, and close the source. Place our overlay across the crop. Verify exact crop boundaries, own-overlay exclusion, no wrong-display/full-screen fallback, correct stale/unavailable handling, unchanged frontmost browser, and unaffected manual controls. Test shortcut conflicts and held-key behavior. This settles crop invalidation and supported window-state rules without purchasing anything.
4. **Packaged release smoke test.** Test the chosen signed/notarized direct package and, if planned, sandboxed/store-development package on a fresh user profile. Check quarantine/Gatekeeper launch, picker/permission identity, revoke/regrant, network access, and upgrade behavior under a stable bundle/signing identity. If Intel is promised, include actual supported Intel hardware; test Apple silicon natively too. Confirm screenshots are absent from app-created files/logs/crash attachments after success, failure, and cancellation. Prove what the app controls; provider retention requires a separate disclosure/contract.
